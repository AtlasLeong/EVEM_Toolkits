# 协同星图战术板设计

日期：2026-09-21。状态：用户已确认产品方向与权限；本文归档设计，不代表已开发、已通过容量测试或获准部署。

## 1. 目标与当前边界

为 EVE 手游局部会战提供组织内私密协同地图：快速上报敌方人数与舰种、确认部队部署、沿星门移动部队，并展示房间在线人员。

保留现有普通星图与寻路功能，增加独立协同入口。公开军团宣传页面不承担战术情报权限；战术组织可以由多个军团成员组成。

已讨论的路线：

- 共享标记板：简单，但容易把重复上报累计成错误兵力。
- **情报与部队分离的协同板：采用。** 原始观察保留来源，由统帅／指挥整理为可移动部署。
- 完整指挥中心：友军编制、作战箭头、战术回放、自动识图等留到后续。

## 2. 已确认权限

| 能力 | 统帅（组织创建者） | 指挥 | 斥候 |
| --- | --- | --- | --- |
| 批准／拒绝加入申请 | 是 | 是 | 否 |
| 任命指挥、调整角色、移除成员 | 是 | 否 | 否 |
| 查看房间人数和具体人员名单 | 是 | 是 | 仅人数 |
| 编辑共享战区范围 | 是 | 是 | 否 |
| 上报情报、修改自己的上报 | 是 | 是 | 是 |
| 确认情报、编辑／移动部队部署 | 是 | 是 | 否 |

- 邀请链接用于申请加入，不能绕过审批直接读取情报。
- 审批通过统一成为斥候。客户端提交的角色字段不得改变这一结果。
- 指挥的审批权不包含任命、降级、移除成员或转让组织。
- 统帅／指挥可以处理情报，但不能改写原始报告的作者和原始观察历史。
- 斥候修改已被采纳的报告时，产生更正并提醒统帅／指挥，不自动覆盖确认部署。
- 审批、角色变化、部署操作保留操作人和服务端时间。
- 待确认的恢复规则：建议统帅移除的成员先由统帅恢复资格，不能由指挥直接再次批准，避免审批绕过移除决定。普通自行退出与管理移除应分开记录；此建议尚不视为用户批准的“封禁”功能。

## 3. 加入与在线人数

组织成员资格与房间在线状态分开。一个组织可以有多个会战房间。

每房间最多 **100 个在线账号**；同账号多个标签页／设备在同房间计一人，不按连接数计算。

房间顶栏显示“在线 36 / 100”。统帅／指挥可打开人员面板，按角色筛选、按昵称搜索，查看昵称／游戏角色名、角色、在线／重连中状态、进入时间和最近上报时间。不显示邮箱、IP 等无关账号信息。

设计约束：

- 服务端原子地办理入场、去重和名额释放，不能先数人再插入。
- 短时断线有重连宽限期；宽限期间保留名额，界面显示重连中，过期释放。
- 同一账号关闭一个页面不导致其他仍在线页面被移出名单。
- 100 人满员时明确拒绝第 101 个新账号；已占名额账号重连不误判满员。
- 不承诺为统帅保留额外第 101 席，也不默认踢出其他成员为其腾位。
- 统帅／指挥在房间外仍能访问其已获授权的审批与人员管理面板；满员不能令人员管理失效。这不额外授予满员房间的地图订阅名额。
- 人数与名单来自同一服务端快照版本；斥候的接口及推送载荷也不包含完整名单，不能仅靠界面隐藏。
- 被移除、降权、账号退出后，后续读写和订阅重新校验权限；不能继续沿用加入时的授权。

实施前需要明确的隔离边界：组织内所有成员是否默认可看该组织的全部房间，还是按房间分别授权。现有确认只覆盖组织加入审批，不能据此默认扩大到全部房间。实施计划先采用显式房间准入模型，授权规则确认前不开放跨房间读取。

## 4. 情报与部署

### 原始情报

记录房间、作者、星系 ID、实际观察时间、服务端接收时间、人数、舰种数量、备注、修订版本及处理状态。

首批快捷舰种：巡洋舰、战列舰、轻型航母、突击航母、无畏舰、重型航母、泰坦，以及其他／未知。舰种键与中文显示名分离；后续可接舰船目录，首版不依赖装配模拟器。

- 人数与已确认舰船数量分别填写，不要求二者相等。
- 未知值使用空值，不等同于零；拒绝负数、小数、非有限数和超出配置上限的数量。
- 上报立即呈现为“待确认”，提交状态与服务端确认分开。
- 相近时间、同星系的上报可提示关联，但不自动相加，也不自动认定为同一部队。
- 修改自己报告仍要携带版本；保留修改历史，而非抹去旧观察。

### 已确认部队

部队有稳定 ID、代号、当前星系、人数、舰种构成、来源报告关联、版本、最后观察时间及操作记录。同一星系允许存在多支部队。

来源关联必须保存被采纳的报告版本，不只是报告 ID。斥候更正原报告的地点也不能变相移动已确认部队。

统帅／指挥选择“确认为新部队”或“关联已有部队”，并明确确认新数量是替换估计还是仅追加来源。首版不提供盲目累加兵力功能。

部署编辑、关联报告、审计记录及待推送事件必须原子提交。失败不出现只更新一半的部署。

## 5. 移动部队与局部地图

拖动部队标记时高亮真实星门相邻星系；落点合法才提交移动。保留部队 ID、人数、舰种、来源与历史，不执行删除再创建。

- 服务端以完整星门数据核验相邻关系，不信任客户端或局部加载结果。
- 普通拖动仅表示整支部队沿星门移动，不代表拆分，也不代表真实路径已被游戏验证。
- 非相邻位置修正使用单独操作并填写原因，不能伪装成星门移动。
- 移动不刷新人数／舰种的观察时间；位置更新时间与兵力确认时间分别显示。
- 两名指挥同时移动同一部队时，只有匹配版本的操作成功；另一方收到冲突，不能静默覆盖。
- 拆分、合并和跨越多跳的批量移动留作后续。

共享战区支持选择一个／多个星域，以及可选 0、1、2 跳边界。后端返回对应局部图，不能下载全宇宙后仅在前端隐藏。

局部图要带边界出口信息；部队跨出可见范围保留记录，并在“战区外”列表显示位置和时间。改变范围不删除报告或部署。切换战区不会强制改变其他人的镜头。

现有寻路继续使用完整图。路径离开当前可视战区时给出提示，不把“未加载”误判成“不可达”。静态图可按数据版本缓存，房间情报必须按账号、组织、房间隔离缓存。

## 6. 页面交互

- 顶栏：房间名称、战区选择、连接状态、在线人数、成员入口（按权限）。
- 主区：地图与部队标记，按缩放聚合，不能因大量标签挤满星系名称。
- 右侧可收起面板：选中星系、快捷上报、部队详情、待确认情报。
- 轻量操作记录：展示确认、修正和迁移，不让高频在线心跳挤占战术记录。
- 快捷上报先带入星系，再填人数与舰种；键盘可完成，避免依赖拖动才能操作。
- 手机不加载完整地图，提供情报列表、星系搜索上报、部队详情与路径规划；有权限者可以选择目标星系执行移动。
- 延续现有整体视觉，不在本阶段重做网站品牌和全局布局。

断线、提交中、发送失败、版本冲突、权限撤销必须可辨识。未收到服务端确认的修改不能展示为全员已同步；恢复连接后先校验权限、补齐状态，再恢复操作。

## 7. 与现有代码衔接（已检查）

- `front-codex/src/pages/TacticalBoard.jsx` 和 `src/components/tactical/TacticalStarMap.jsx` 为现有地图入口／Canvas；优先复用绘图与命中能力，协同状态独立封装。
- `front-codex/src/services/apiTacticalBoard.js` 当前访问静态全量图接口；新增局部图接口，不改变旧接口默认语义。
- `backend/TacticalBoard/models.py` 的四类星图模型为 unmanaged 静态表；不在它们上混入协同房间数据或破坏原表。
- 新增独立 Django 应用建议名 `TacticalCollaboration`，协同数据使用默认业务库，不写入独立授权库。
- 使用 `settings.AUTH_USER_MODEL`，不可依赖 CI 中的 `auth.User` 就认为生产自定义用户模型已兼容。
- 复用现有 `fetchWithAuth.js` 会话隔离；退出或切换账号要关闭连接、清空私密缓存、丢弃旧账号延迟回包。
- 部署示例目前为 Gunicorn 三个 WSGI worker；标准 `asgi.py` 存在，但没有已建成的战术 WebSocket 链路。不能宣称现有部署已支持 100 人实时协同。

## 8. 技术实施建议（不是容量承诺）

比较三种同步方案：普通增量轮询改动较小但延迟／空请求较多；SSE 适合单向通知但仍需单独命令和在线租约；WebSocket 适合持续协作但需增加长连接运行与发布保障。

推荐在隔离环境验证“HTTPS 命令 + WebSocket 增量通知 + 持久化事件游标”。具体 ASGI 运行时、共享连接层和版本要在实施选型时查验官方兼容性，不在本文安装依赖或修改线上服务。

必须满足：

1. 数据库为事实源；命令包含 `request_id` 和 `expected_version`，重复请求不产生第二次上报／移动，同键不同载荷拒绝。
2. 事件与业务修改同事务落库，再通知连接；断线按房间游标补齐，超出保留窗口则重取快照。
3. 快照与游标一致；同版本事件去重，缺口触发补齐，不能只靠内存广播维持正确性。
4. 跨 worker 的在线去重、满员判断和权限撤销使用共享原子状态；内存单进程表不能作为发布实现。
5. 每次命令、入房、补齐和敏感推送都按当前身份及资源归属授权。长连接认证设置有效期；长期令牌不得放入可被代理日志记录的 URL。
6. 限制请求长度、上报频率、连接数和待发送队列；慢客户端可以要求重取快照，不能无限累积事件。
7. 同组织不同房间的事件、报告、部队 ID 不能交叉引用。浏览器隐藏入口不代替后端授权。
8. 故障时显示降级／断线；不静默把离线修改当作共享真值。恢复机制不能绕过房间容量和权限。

## 9. 验收与交付边界

- 三角色完整权限矩阵、指挥审批默认斥候、并发审批仅一次生效、移除后所有连接失权。
- 99→100→101 并发入场、多标签去重、关掉单标签、重连宽限、超时清理、共享状态重启。
- 两位指挥同时移动、重复提交、移动后重放、确认与修改报告竞态；任何一步不得凭空新增人数。
- 局部星域实际响应体裁剪、边界出口、战区外部队保留、旧寻路与普通星图回归。
- 真实多用户客户端验证跨进程同步；网络中断、乱序／重复通知、补齐窗口过期、身份切换与慢消费者。
- 桌面和手机交互测试，以及真实 MySQL 事务／约束测试。SQLite 单测不代替 MySQL 并发验收。
- 100 个独立账号持续在线的负载测试记录延迟、失败率、CPU、内存、数据库负载及恢复表现。具体负载模型和门槛在测试方案中明确，未经测试不标记“支持 100 人”。
- 开发、评审和本地演示先行。合并、推送、线上迁移、Redis／ASGI／代理配置及发布需另行授权。

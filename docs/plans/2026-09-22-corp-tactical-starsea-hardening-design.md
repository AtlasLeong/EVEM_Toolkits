# 军团、战术板、星海见闻加固设计

**目标**：在不破坏本地预览和现有 HTTP fallback 的前提下，完成阶段 0/1/2 的安全、实时协同和移动端体验修复。

## 设计决策

采用“ASGI WebSocket + Redis 事件广播 + 单调版本号 + HTTP fallback”方案。

- 阶段 0 先修正角色权限、登录回跳、生产 Origin/Host、上传边界和 ASGI 启动配置。
- 阶段 1 为每个战术组织维护 `state_version`。命令事务提交后发布变更事件；WebSocket 只在版本变化时推送，HTTP fallback 使用版本游标。快照读取不再锁组织行。
- 阶段 2 将普通人数上报作为地图观察标记，加入地图/列表联动、冲突差异提示、移动端快速上报和离线重试；地图使用视口过滤和分层显示。

## 权限模型

- 统帅：组织范围、成员角色、全部部署和上报管理。
- 指挥：审核/移除斥候、编辑部署和上报；是否可调整作战范围由组织策略显式配置。
- 斥候：只能创建和修改自己的 `system_count` 人数上报；禁止 `fleet_intel`、舰船明细、`force_id` 和他人记录编辑。

## 实时数据流

1. 客户端发送带 `request_id` 和 `expected_version` 的 HTTP 命令。
2. 服务端在短事务中校验权限、版本并写入数据，同时递增 `state_version`。
3. 事务提交后向 Redis/Channels 发送组织版本事件。
4. WebSocket 客户端按版本拉取角色过滤后的增量/快照；无 Redis 或 WebSocket 不可用时，客户端按版本轮询。
5. 客户端只接受更大的 `state_version`，服务端时间戳仅用于显示。

## 移动端交互

- 地图继续隐藏，保留按星系分组的部署与上报列表。
- 固定底部“快速上报”按钮打开 bottom sheet。
- 默认最近使用星系，人数快捷键和发送状态明确显示。
- 网络失败进入本地 outbox，恢复后按原 `request_id` 重试。
- 成员和历史记录使用游标分页/虚拟列表。

## 非目标

- 本阶段不迁移生产数据库，不改星海见闻内容模型，不重做军团视觉主题。
- 不强制本地预览必须依赖 Redis；本地无 Redis 时使用可观测的 HTTP fallback。

## 验收标准

- 斥候越权创建舰队部署返回 403，并且前端不显示对应输入。
- WebSocket 连接每次只在版本变化时收到更新；100 个连接不会持续锁同一组织行。
- 普通人数上报在地图和列表同时出现，点击地图标记能定位上报记录。
- 版本冲突显示字段差异并允许选择服务器值或本地值。
- 390px 宽度可完成快速上报，断网后能够恢复发送。
- 登录后能安全回到原战术组织 URL。
